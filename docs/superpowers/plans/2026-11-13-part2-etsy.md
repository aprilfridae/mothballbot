# Part 2: Etsy Connector (plus shared email and browser groundwork) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Mom can post an approved draft to Etsy as well as eBay. Etsy buyer messages show up in `buyer: {username} · Etsy` threads, and your replies go back. Etsy sales reach `#to-ship` and Mom's Telegram, and her 📦 Shipped uploads tracking to Etsy. Whichever platform sells first, the bot ends the listing on the other one.

**Architecture:**
- **Etsy Open API v3** handles listings, receipts (sales) and shipments. Etsy has no messaging API, so messages use the spec's email-then-browser path.
- **Shared groundwork, built here and reused by Part 3 (Facebook):**
  - `email/`: a dedicated Gmail inbox read over IMAP every 2 minutes. Each notification email becomes a typed `MailEvent`.
  - A new **`worker` container** (Playwright, real Chrome with a visible window on a virtual display, noVNC). It owns every browser session and exposes a small HTTP API on the internal Docker network only. Requests run one at a time per platform.
  - A **browser-health path.** On a login wall, checkpoint, CAPTCHA or unrecognised page, the worker pauses that platform, and the app posts the screenshot to `#bot-status` with a **▶️ Resume** button.
- **Connector registry.** `main.ts` currently wires eBay function by function (`send: { ebay }`, `fulfill: { ebay }`). This plan adds a `connectors: Partial<Record<Platform, PlatformConnector>>` map and moves eBay behind it, so each new platform is one registry entry.
- **Multi-platform posting and cross-delisting.** Posting moves from item level to listing level (one row per item × platform). A sale on any platform ends the item's other live listings. Spec §8 put delisting in Part 5, but it moves here: once a second platform goes live, double-selling becomes possible.
- **Task order follows spec §8 (steps 2–5), and nothing waits on Etsy's app approval.** Tasks 1–4 (registry, worker, inbox, Etsy messages and replies) only need the Gmail and browser blocks plus `ETSY_USERNAME`. Tasks 5–7 (API auth, Etsy draft fields and buttons, posting, sales and delisting) need the approved Etsy keys. **Apply for the Etsy app before starting Task 1**, so approval runs in parallel.
- *Plan call:* the app talks to the worker over HTTP (`http://worker:7070`) instead of through pg-boss jobs. Replies need an answer straight away (✅/❌), and Discord stays in the `app` process only. Durability comes from the app's existing pg-boss jobs, which retry worker calls.

**Tech Stack:** unchanged from Part 1, plus `imapflow` and `mailparser` (email), `playwright` (worker only), and the `mcr.microsoft.com/playwright` base image with Google Chrome, Xvfb, x11vnc and noVNC.

**Spec:** `docs/superpowers/specs/2026-11-13-selling-bot-design.md` (§6 Platforms table, Browser automation rules, Sale flow; §8 build order steps 2–5 for Etsy). Earlier plans: `2026-11-13-part1-ebay-foundation.md`, `2026-11-13-part1b-mom-approval-pricing.md`.

## `.env` additions

Each block is **all-or-nothing**, like eBay: fill every key in a block, or none. A half-filled block stops startup and lists the missing keys.

```bash
# ── Etsy messages (works before app approval; needs the inbox and worker blocks) ──
# Your Etsy username, so your own messages aren't mirrored as buyer messages
ETSY_USERNAME=

# ── Etsy API (fill all of these, or none while app approval is pending) ──
ETSY_KEYSTRING=
ETSY_SHARED_SECRET=
ETSY_REFRESH_TOKEN=
ETSY_SHOP_ID=
ETSY_SHIPPING_PROFILE_ID=
ETSY_RETURN_POLICY_ID=
ETSY_READINESS_STATE_ID=

# ── Notification inbox (needed for Etsy and Facebook messages; all or none) ──
GMAIL_ADDRESS=
GMAIL_APP_PASSWORD=

# ── Browser worker (needed for Etsy and Facebook messages; all or none) ──
# Password for the remote browser view at http://<homelab>:6080
VNC_PASSWORD=
```

What runs with which blocks:
- **`ETSY_USERNAME` + inbox + worker (before approval):** Etsy buyer messages and replies.
- **Etsy API only:** posting, sales, tracking and delisting work. `#bot-status` says once that Etsy buyer messages need `ETSY_USERNAME` and the inbox and worker blocks.
- **Everything filled:** all of it.
- **`ETSY_USERNAME` without the inbox or worker:** startup stops with `Etsy messages need the Gmail and browser blocks in .env: …`.
- **Inbox + worker without any Etsy keys:** allowed (Part 3 uses them for Facebook). Etsy emails are ignored.

`WORKER_URL` is set in `docker-compose.yml` (`http://worker:7070`) and isn't a secret, so it isn't in `.env`.

## Global Constraints

- **Unchanged from Parts 1 and 1b:** only `OWNER_DISCORD_ID` in Discord and Mom's linked chat on Telegram. Never fail silently (`#bot-status`). Never post twice, and dedupe on platform IDs. Every reply gets ✅ or ❌ with a reason.
- **Buyer thread name:** `buyer: {username} · Etsy` (`PLATFORM_LABEL.etsy`), truncated as in Part 1.
- **Etsy limits:** title ≤140 characters, at most 13 tags of ≤20 characters each, at most 10 photos, quantity 1.
- **Etsy eligibility:** this shop sells on Etsy only as **vintage** (20+ years old). An item the draft doesn't mark vintage gets no Etsy button until Mom sets an era with Edit → Era.
- **Etsy tokens:** the access token lasts 1 hour. Every refresh returns a **new refresh token**, which is saved in `settings` (`etsy.refreshToken`) and used from then on. The `.env` value only seeds it, or replaces it when you change `.env`.
- **Browser rules (spec §6):**
  - Real Chrome with a persistent profile per platform on the `browser-profiles` volume, running only on the home IP.
  - One action at a time per platform, with random 2–6 s pauses between steps and typing at 60–180 ms per character.
  - The worker **never fills in a sign-in form.**
  - Any unexpected page pauses the platform and reports it with a screenshot.
- **Etsy browser visits only happen when an email arrives.** There is no polling of Etsy pages.
- **noVNC and the worker API are LAN/internal only.** noVNC binds to the homelab's LAN address with a password. The worker API has no host port.
- **Selectors** for each site live in one file (`worker/sites/{site}/selectors.ts`), so a layout change is a one-file fix.

## Review Focus

1. **Etsy and eBay sell the same item within minutes.** Both sales are recorded and announced, and the second gets a loud `#bot-status` warning ("Sold twice: item #12 on eBay and Etsy, cancel one"). Delisting never ends a listing that already sold. → Task 7
2. **Etsy's rotated refresh token.** A restart right after a refresh must use the new token from `settings`. Editing `.env` to a freshly minted token must win over the stored one. → Task 5
3. **The same email processed twice** (IMAP reconnect, the overlap window), or a message seen both in the email and in the fetched thread. One Discord post per buyer message. → Task 3, Task 4
4. **The worker is down, paused or slow.** A reply gets ❌ "Etsy is paused: needs a sign-in, see #bot-status", never a hang (30 s timeout). A thread fetch is retried by the job, not lost. → Task 2, Task 4
5. **A vintage-looking item that isn't 20+ years old, and missing Etsy fields.** No Etsy button without an era. When Etsy rejects a listing, its own message reaches Mom with ✏️ Edit, exactly like eBay. → Task 6, Task 7

### Task 2: Browser worker container, pause and resume

**Files:**
- Create: `docker/worker.Dockerfile`, `src/worker/main.ts`, `src/worker/browser.ts`, `src/worker/guard.ts`, `src/browser/workerClient.ts`, `src/tools/captureFixture.ts`
- Modify: `src/config.ts`, `.env.example`, `docker-compose.yml`, `package.json` (scripts `start:worker`, `test:browser`), `src/discord/status.ts`, `src/discord/bot.ts` (Resume button), `src/db/schema.sql`, `src/db/repo.ts`
- Test: `tests/worker/main.test.ts`, `tests/browser/workerClient.test.ts`, `tests/browser/guard.browser.test.ts`

**Interfaces:**
- **Produces, config:** `Config.worker: {url, vncPassword} | null`, all-or-nothing like `EBAY_KEYS`. Add the browser worker block to `.env.example`.
- **Produces, worker (`node dist/worker/main.js`):**
  - It listens on `:7070` on the Compose network only.
  - `POST /{site}/{action}` with a JSON body returns `{ok:true, result}`, or `{ok:false, kind:'paused'|'blocked'|'error', message, screenshot?}`. The screenshot is a base64 PNG.
  - `GET /health` returns each site's `{site, paused, reason, since}`. `POST /{site}/resume` clears the pause after a quick check that the session is signed in.
  - **Per-site serial queue:** requests for one site run one at a time, and other sites run alongside them.
  - Pause state lives in Postgres table `browser_pauses (site primary key, reason, screenshot_path, since)`, so it survives restarts.
- **Produces, `browser.ts`:**
  - `openSite(site) → Page`, using `chromium.launchPersistentContext('/profiles/{site}', {channel:'chrome', headless:false, viewport:null, locale:'en-US', timezoneId:'America/Los_Angeles'})`. It runs on the Xvfb display, which noVNC shows. The context is reused between requests and closed after 10 idle minutes.
  - `pause(min, max)` waits a random time. `humanType(locator, text)` types each character with a 60–180 ms delay. `humanClick(locator)` scrolls into view, hovers and clicks.
- **Produces, `guard.ts`:** `checkPage(page, site) → void | throws BrowserBlocked{reason:'login'|'checkpoint'|'captcha'|'unknown-page', screenshot}`.
  - It matches login URLs and form fields, CAPTCHA iframes and checkpoint URLs from the site's selectors.
  - Every site action calls it after each navigation. `'unknown-page'` covers an expected element that doesn't appear within 15 s, which is how layout changes show up.
- **Produces, app side:**
  - `createWorkerClient(url, fetchFn) → {call(site, action, body, timeoutMs = 30_000)}`.
  - It throws `BrowserPausedError(site, reason)` for paused or blocked results, and `WorkerError` for errors and timeouts.
  - `reportBrowserPause(site, reason, screenshot)` posts once per pause to `#bot-status`: `Etsy needs you: {reason}. Open http://192.168.1.8:6080 (password in .env), fix it, then tap Resume.` It attaches the screenshot and a **▶️ Resume Etsy** button (owner only), which calls `/{site}/resume` and edits the post to show the result.
  - The noVNC address comes from `NOVNC_URL` in `docker-compose.yml`, which defaults to `http://<host LAN IP>:6080`.
  - `captureFixture site url name` saves the current page's HTML from the worker profile into `tests/fixtures/{site}/{name}.html`, with names, emails and addresses replaced by placeholders, for the browser tests.
- **Docker:**
  - The worker image is based on `mcr.microsoft.com/playwright` (Node 22, Ubuntu), with `npx playwright install chrome`, `xvfb`, `x11vnc`, `novnc` and `websockify`. An entrypoint starts Xvfb `:99`, x11vnc with `-rfbauth` from `VNC_PASSWORD`, noVNC on 6080, then the worker.
  - `worker` service: `env_file: .env`, `shm_size: 1gb`, volume `browser-profiles:/profiles`, `ports: ["192.168.1.8:6080:6080"]` (LAN only; the README tells you to change the IP if yours differs), and no port 7070 on the host.
  - `app` gets `WORKER_URL: http://worker:7070`.
  - *Verify while implementing:* that Google Chrome installs on the homelab's CPU architecture. On arm64, fall back to Playwright's Chromium and note it in the README.

### Task 7: Etsy listings, sales, tracking, and cross-platform delisting

**Files:**
- Create: `src/platforms/etsy/listings.ts`, `src/platforms/etsy/orders.ts`, `src/platforms/etsy/connector.ts`

**Interfaces:**
- **Produces, Etsy listings:**
  - `findTaxonomy(etsy, query) → taxonomyId`, from `GET /seller-taxonomy/nodes`. The tree is cached in memory for a day and matched on the deepest node whose name contains the most query words.
  - `createListing(input)`:
    - `POST /shops/{shop}/listings` with `quantity:1`, `title` (≤140), `description`, `price`, `who_made:'someone_else'`, `when_made`, `is_supply:false`, `taxonomy_id`, `tags`, `materials`, and the shipping, return and readiness IDs.
    - Then `POST /shops/{shop}/listings/{id}/images` for each photo (multipart, max 10; HEIC converted to JPEG with sharp).
    - Then `PATCH …/listings/{id}` with `state:'active'`.
    - The URL is `https://www.etsy.com/listing/{id}`.
    - If any step after the draft fails, the draft listing is deleted, so no stray drafts pile up in Shop Manager.
  - `delist({externalId})` sends `PATCH state:'inactive'`. A 404 or an already sold-out listing returns `'already-gone'`.
- **Produces, Etsy orders:**
  - `fetchNewOrders(since)` calls `GET /shops/{shop}/receipts?min_created={unix}&was_paid=true`. Each receipt maps to a `PlatformOrder`:
    - address from `name`, `first_line`, `second_line`, `city`, `state`, `zip`
    - `shipBy` from the transactions' `expected_ship_date`
    - `lineItemIds` = transaction IDs
    - `sku` from `transactions[0].sku`
  - The item is found from the order by `listing_id` with `repo.findItemByListing('etsy', listingId)` when `sku` is empty.
  - `fulfill(order, tracking, carrier)` calls `POST /shops/{shop}/receipts/{id}/tracking` with `tracking_code` and `carrier_name`, mapping `USPS→'usps'`, `UPS→'ups'`, `FedEx→'fedex'`. With no tracking, it does nothing, because Etsy has no "shipped without tracking" call.
  - *Verify while implementing:* check the carrier names against Etsy's list.
- **Produces, pipeline:**
  - `postItem(itemId, platform|'all', deps) → Record<Platform, PostResult>`.
  - The guard is per listing: `repo.transitionListing(itemId, platform, from: ['none','error'], to: 'posting') → boolean`, where `'none'` means no row yet. A live listing is never re-posted or downgraded.
  - The item status becomes `live` once any listing is live, and stays `error` only when no listing is live and the last attempt failed.
  - `'all'` posts the offered platforms one after another, never in parallel.
- **Produces, sale handling:**
  - `onSale(order, deps)` runs inside `announceOrders` after a *new* order is inserted. It finds the item (from the SKU or the listing), then for every other listing row that is `live`, calls `connectors[p].delist` and marks the row `ended`.
  - It posts `💰 Sold on Etsy: {title} · removed from eBay` to `#sales`.
  - A delist failure posts `⚠️ Couldn't remove item #12 from eBay: {reason}. End it by hand.` to `#bot-status`, and the sale still goes through.
  - **Sold twice:** when the item already has an order from another platform, the bot skips delisting and posts `⚠️ Sold twice: item #12 on eBay and Etsy. Cancel one of them.` to `#bot-status` **(RF1)**.

  - `listings.status` can now be `posting | live | error | ended`.

  - `CREATE INDEX IF NOT EXISTS listings_external ON listings(platform, external_id)`.
